演讲标题叫 “Now More Than Ever”。Ron 开场就自嘲：这是那种“世界变了，所以我以前说的那些东西现在更该做了”的老派演讲。他讲的三件事都不新：类型系统、测试、代码评审。新的是他给出的理由：agent 写代码以后，这三件事不但没过时，反而更重要。最后他还讲了一个 Jane Street 自己的转变：过去二十多年一直说对形式化方法不感兴趣，现在开始认真考虑了。

## Jane Street 是什么样的地方

先交代背景，因为后面很多判断都和这家公司的处境有关。

Jane Street 是一家全球交易公司。Ron 刚加入时公司大约 35 人，现在大约 3,500 人，其中大约 2,000 人日常写代码。他给的规模数字是：美股成交量的约 10%，美国期权的约 8%，欧洲 ETF 的约 20%，每天交易额是几千亿美元。

在这种地方写程序，出错的代价很直接，所以公司对工程的严谨程度要求很高。不过 Ron 特意补了一句：严谨要和价值挂钩，不同系统该投入多少审查和小心，要看出错的代价。

另外两个特点：

- **很 AI。** 几年前就成立了 AI assistant 团队，给工程师做 agent 和 LLM 工具。Ron 坦白说，很长时间里这件事对生产力是净损耗，模型不够聪明。直到去年 11 月左右，模型突然越过了门槛。他的比喻是：风没起的时候造帆船，造了很久，然后风终于来了。现在他对做开发工具的人说：“我们现在都是 AI assistant 团队了”，做工具不考虑 agent 就是没尽到职责。
- **很 PL。** 主力语言是 OCaml（机器学习和数据脚本用 Python），还在 OCaml 上做了自己的扩展，叫 OxCaml。

## 一、类型：不只是检查“管子接没接对”

很多人觉得类型系统就是检查参数类型有没有传错。Ron 认为这严重低估了它。

类型系统先给你一批“开箱即用”的保证：OCaml 里没有空指针错误，没有越界访问。OxCaml 进一步提供了类型安全的栈分配和数据竞争防护。但更重要的一步，是不再把类型当成“在旁边打手心的保姆”，而是当成设计的一部分：用类型来表达和强制程序里的不变量。

他举了两个例子。

第一个是 XSS。用普通字符串插值拼 HTML，用户输入没转义，就有注入风险。正确的写法不难，记得调用转义函数就行，但更好的做法是让错误写不出来。Jane Street 的 OCaml Web 框架里，HTML 模板中插入字符串必须经过 `Node.text`，它会做转义；漏写就是类型错误。

![XSS-protection 幻灯片：用 %html 模板和 Node.text 让未转义的用户输入无法通过编译](./xss-protection.webp)

单看这几行代码，好像很简单，自己注意一点就行。Ron 强调的是类型的“远距离作用”：错误可能发生在很多层代码里的任何地方，而类型是一个全局系统，保证哪儿都不会犯这个错。

第二个例子是他提出过的那句口号的变体：make illegal states unrepresentable（让非法状态无法表示）。网络团队有一个描述交换机接口配置的类型，最初照着交换机配置的样子建模成一串命令：MTU、shutdown、IP 地址。问题是 MTU 和 shutdown 只应该出现一次，IP 地址可以出现多次，而命令列表允许任意重复。计算“有效 MTU”的函数于是要面对一个说不清的问题：shutdown 出现两次怎么算，MTU 取第一个还是最后一个？

改法是把能出现零次或一次的字段变成 `option`，能出现多次的变成 `list`。非法配置没法再构造出来，计算函数也变得简单、清楚。

![Making illegal configs unrepresentable 幻灯片：改写后的 Interface.t 记录类型和更简单的 effective_mtu 函数](./illegal-configs.webp)

### 类型对 agent 意味着什么

Ron 的核心论点是：agent 依赖反馈，无论是用的时候还是训练的时候。类型系统正好提供了两种好反馈：

- **即时的上下文。** 模型的上下文窗口有限，一百万 token 听着很多，其实不够装下所有该知道的东西。类型错误会在需要的时候把相关信息送到面前，agent 也可以用工具去查类型。
- **快。** 类型检查比任何测试套件都快，所以 agent 可以快速迭代。

另一方面，LLM 是随机的，记忆也有限。他举的例子很实在：一开始告诉模型构建命令怎么调用，23 万 token 以后它可能就忘了，更别说系统里那些横切的复杂不变量。用一个小的类型化内核（small typed kernel）把全局规则写死，就能给模型它自己做不到的一致性。他引用了很多人都在说的一句话：验证现在是关键瓶颈。

![Types and agents 幻灯片：agent 依赖反馈，LLM 随机且记忆有限，小的类型内核可以强制全局规则，验证是关键瓶颈](./types-and-agents.webp)

## 二、测试：expect test 和库级确定性模拟

Jane Street 的测试手段很全：单元测试、QuickCheck 属性测试、AFL 模糊测试、用 Antithesis 做的全系统确定性模拟测试、生产和开发环境并排对比、用历史数据回放的测试床。Ron 说这些在场的人大概都认同，他想讲的是两件比较“怪”的做法：expect test，以及库级别（而不是全系统）的确定性模拟。

### expect test 是什么

做法很简单：测试里把东西打印出来，测试框架把输出捕获在测试代码里。第一次运行时 expect 块是空的，测试失败，框架给出 diff，你确认后它把实际输出写回源码，测试就通过了。之后输出一变，测试就失败，diff 直接显示行为变了什么。

Ron 承认这听上去像个坏主意：看起来鼓励偷懒（跑一下，看着差不多就收下），而且它把你往基于例子的测试推，而不是大家公认更好的属性测试。（他补充说 expect test 里也可以做属性测试，他们也在做。）但他的结论是：expect test 很好用，因为它最大的价值是**帮人理解被测程序**。

关键在于输出要精心设计成人能读懂的样子。直接把一大堆输出倒出来，没人看得懂，等于什么都没做。下面这个例子把几个报价参数打成一张表：

他最喜欢的例子来自硬件工程师：他们习惯看示波器，于是就有了纯文本的“示波器”。Ron 说自己看不太懂，但硬件工程师很依赖它来理解电路的细节行为。

### 库级确定性模拟

另一个做法是把程序切成片段，在确定性环境里运行。网络、时钟、其他服务都可以模拟。这样反馈只需几毫秒，而不是几分钟或几小时。Ron 的看法是：把 17 小时的测试压到 7 分钟当然好，但让它感觉像是瞬间完成，会让开发过程完全不一样。

模拟环境也能测分布式系统。下面这个例子把一个客户端、一个代理和一个 echo server 接在一起，trace 里一眼就能看出一个奇怪现象：客户端要等约 5 秒才连上，因为服务发现组件（trace 里的 tloc）第一次广播需要几秒。

![Tracing a simulated distributed system 幻灯片：客户端、代理和 echo server 的模拟 trace，大约在 5 秒时才完成连接](./simulated-distributed-trace.webp)

### 为什么例子测试比听上去有效

Ron 专门为基于例子的测试辩护了一段，题目借用了那句 “unreasonable effectiveness”。他的理由是：

- 大多数软件很脆，错一点往往就错很多。这对系统本身是坏事，对测试却是好事：少量例子就能抓住很多问题。
- 类型让代码更“刚性”。类型的结论处处成立（他说这是全称量词 ∀ 的力量），写得好的代码会有一种“咔嗒一声卡到位”的感觉，少量测试就能证明很多性质。
- 选在哪里按一下，需要人的判断。他部分同意上一位讲者说的“针对接口测试”，但认为实现里的怪异之处往往是软件的软肋，测试时考虑一下实现也有帮助。
- 提交到仓库里的例子不只说明行为，还说明意图：有人认为这个例子值得写下来。

### 测试对 agent 意味着什么

expect test 是另一种“闭环”。做 agent harness 的人常说要把所有能闭的环都闭上，让 agent 尽可能自己完成流程。expect test 让 agent 看到自己的改动在多个层次上改变了什么行为；这些输出会随仓库长期保留；而且是纯文本，对 agent 很友好。Ron 说模型虽然是多模态的，但视觉能力还不够好，把信息转成文本对它们更友好。

对人也一样：agent 交来的 diff 不只有代码的变化，还有代码引起的行为 trace 的变化。

他用 Excel 来讲这一点。普通程序把逻辑写得紧凑，但数据流和行为看不见；电子表格相反，逻辑散在各个单元格里，数据却一直摆在眼前。他早年在 Jane Street 不止一次被用电子表格的人比下去，对方做得更快，调试也更清楚。expect test 兼得两边：既能看紧凑的逻辑，也能看展开的行为。

## 三、代码评审：比以往更重要

Ron 说，他刚到 Jane Street 时以为评审就是为了正确性，别在循环里犯蠢亏一大笔钱。后来发现评审做的事多得多：抓 bug、传播最佳实践、提高 bus factor、让代码保持简单。

他认为“为读者而不是为写者优化”会改变一切：代码更简单、更灵活、更好维护、bug 更少，也更能抵抗系统变大后各部分互相牵扯（cross-terms）对个人生产力的侵蚀。公司从 35 人长到 3,500 人，他对此体会很深。最后，在一个为“被读”而设计的代码库里工作，本身就是一种乐趣，这也是留住优秀工程师的方式。

### agent 需要好的代码库，却不擅长维护它

Ron 的说法是：代码质量是 agent 生长的土壤。

他举了 Anthropic 用一群 agent 写 C 编译器的实验。他认为这是个很好的实验：编译器能编译整个 Linux 内核，虽然有很多缺口，比如没有类型检查。但他觉得最有启发的是实验怎么结束的：编译器还有很多问题没修，可 agent 越往后越难前进，每改一处就更可能弄坏别处，最后只能停下。他认为这说明了 agent 在混乱代码库里会发生什么。

原因在训练方式：模型被训练成拼命把红灯变绿，它们很擅长这个，会做出看起来很像你要的东西。但代码库还有一堆非功能性质：够不够简单、灵活、可扩展，留了多少隐患，多少该抽取的重复代码和硬编码常量。agent 依赖这些性质，却不擅长保持它们。所以，至少在现阶段，评审比以往更重要。他甚至说，在当下，评审可能是人在软件工程里能做的最重要的事。

![Code quality and agents 幻灯片：代码质量是 agent 代码生长的土壤，agent 依赖非功能性质但不擅长保持它们，评审因此比以往更重要](./code-quality-and-agents.webp)

### 评审 agent 的代码很难

难在几个地方：

- **打破了评审的社会契约。** 以前别人交来一个功能，说明对方花了心思，你会优先评审。现在可能只是对 agent 说了一句“修一下”就丢过来。幻灯片上引用了一位工程师的话，大意是：你只给 AI 写了个 prompt，自己没花功夫理解输出，却要我们替你做，那就请回吧。
- **agent 不会从评审里成长。** 对人的评审也是在带人，对 agent 指出问题，它在这次会话里改了，会话结束就全忘了。（可以写进 skill 或文档，但日常的来回不一样。）
- **注意力很难集中。** 有工程师说，读 AI 生成的代码时自己会走神、眼神发直。
- **reward hacking。** 让它保证测试通过，它可能把测试删了。错误的形态变了，以前代码写得粗糙是一种信号，现在 agent 写的代码表面永远整齐，就像 LLM 写的英文从不犯语法错误，但这不代表内容正确。质量的表面信号和真实质量脱钩了。

![Reviewing agentic code is hard 幻灯片：agent 打破评审的社会契约，不会从评审中学习，情感上很难投入](./reviewing-agentic-code.webp)

### 但 agent 也能帮评审

- 改进代码质量变便宜了。有工程师说，现在更愿意在评审里提大一点的重构要求，因为那不再显得不可能或刻薄。
- 可以让 agent 把大功能拆成一串更好读的小改动，或者补上说明性的测试。
- 可以把 agent 当作问答对象先摸清代码（它会说点小谎，但能很快帮你理清思路），再去找人讨论，讨论质量更高。
- 他们还在试一种做法：让 agent 为一个功能设计一份“导览”，按什么顺序看哪些 diff，每一步讲什么，减轻读代码的负担。

## 四、新变化：Jane Street 开始考虑形式化方法

前面都是“老东西更重要了”。最后这部分是真的变了。Ron 说过去这么多年他一直在让人失望：我们喜欢类型系统和好语言，但对形式化方法完全不感兴趣。现在这个立场在变，原因是成本结构变了。

他用 seL4 说明过去的成本：8,700 行 C，大约 25 人年，还要做大量工具；作者说如果重做也许 10 人年就够。折算下来，每行代码大约 23 行证明、半个人日。只有极少数需要极高保证的系统才值得这样做。

![The costs of formal verification 幻灯片：seL4 用 25 人年验证 8,700 行 C，大多数软件负担不起，但纯数学领域的结果越来越强](./formal-verification-costs.webp)

变化的信号来自数学：模型在 IMO、Putnam 这类难题上的进展，以及 Terence Tao 这样的数学家和 agent 配合，在 Lean 里做形式化证明。Ron 的解读很有意思：agent 不一定比专业数学家聪明，但它“背下了整个互联网”，Lean 写得比大多数数学家好。懂领域的人加上一个能把想法翻译成 Lean 的“速记员”，不同专长就能结合起来。他觉得产品设计师现在能自己做出可用原型，是同一类现象。

他强调这是一场赌注，现在的模型还不够强，但值得投入。他列出的方向：

- **Refinement types**：好读、好推理，难写。也许可以让模型负担写注解的工作。
- **差分验证**：不写完整规格，只证明某个改动不破坏某些性质。
- **完整的正确性证明**：从规格出发，让模型写实现并附带证明（比如用 Lean）。用户写一个简单、低效、表达意图的实现，agent 去做一个快得多的实现，并证明两者等价。
- **改造 OxCaml 让证明更容易**：没有共享可变状态的代码不需要分离逻辑（separation logic），更好证明。他以 Rust 上的验证工具 Verus 为例：Rust 的所有权规则消除了大部分共享，所以不需要分离逻辑。

![Potential directions 幻灯片：refinement types、差分验证、完整正确性证明、改造 OxCaml 让证明更容易](./formal-methods-directions.webp)

他说这个想法大约是八周前才冒出来的，他们打算组建形式化方法团队。

## 以人为中心

收尾时 Ron 回到人。有人提出目标是“人不再读写代码”，他觉得这个目标很奇怪。目标应该是让人尽可能高效。在可见的未来，最稀缺的资源仍然是人的注意力。所以工具和流程都该围绕放大个人杠杆来设计：一部分是让 agent 更有效，另一部分，也是讨论得不够的那部分，是让人更容易理解系统在做什么。

## 问答里的几个观点

- **自动化代码评审？** Ron 很支持所谓 AI code review，比如在整个代码树里审计某种坏习惯。但他认为那是 harness 工程的一部分：今天需要多个 agent 互相审查，也许将来更强的模型就不需要了。他所说的评审是为了让人理解系统，这是另一回事。
- **依赖类型？** 他说“旧的我”对依赖类型持怀疑态度：成本和复杂度太高，论文里证明的平衡二叉树正确性也不是他的 bug 所在，那种东西测试就够了。他更看重人体工程学好的类型扩展，比如 OxCaml 的 mode：标成 local 的值保证遵守栈纪律，这本是为了栈分配，但也能做能力式的访问控制。例如在 Bonsai Web 框架里，用一个 local 的能力值把“构建计算图”和“运行”两个阶段分开，在错误阶段改图就过不了类型检查。“新的我”则觉得 agent 可能改变了这笔账，所以对依赖类型和 refinement types 重新有了兴趣。
- **形式化验证会不会束缚开发？** 他说形式化方法要赢，前提是它让人更快，而不是更慢。没按可验证方式设计的程序很难证明，一个重要原因是它多半本来就不正确，而错误的东西没法证明。他看好“构造即正确”的路子：人写简单的实现表达意图，agent 一手拿 Lean、一手拿性能分析工具，去做又快又有证明的版本。每个人都能有自己的性能工程师和证明工程师。
- **代码风格和写作。** 他希望代码风格中立、统一，读起来看不出是谁写的，这样人能在不同项目间流动。写作则相反，个人风格很重要。他希望自己读到的文字是人写的，而不是 LLM 写的。他也提到一个曾经的担心已经消失：LLM 很会模仿周围代码的风格，有时模仿得过头，连坏代码也学。
