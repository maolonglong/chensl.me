同一套模型，在某个工具里表现不错，换到另一个就明显变笨。这一年见过太多“换个环境，模型像换了个人”的例子。解释它的词叫 Harness：Agent 周围那套环境。产品侧怎么设计这套环境，我在[《薄 Agent，厚流程》](/blog/thin-agent-thick-harness/)里写过。本文写另一半：**使用团队自己要维护的那层**。更值得记住的分界是 **Agent ≠ Harness**。

Agent 产品会提供模型循环、工具协议和执行环境，这些是产品自带的。围绕你自己的项目，还需要一套可读、可操作、可验证的工程环境：项目知识、约束、验收方式。这一层不归 Agent 产品管，要由使用团队自己维护。维护方式也很朴素：每次发现 Agent 犯错，就工程化一个方案，让它再也不犯这个错。

过去常把这笔账算在提示词头上，后来发现，大多数“不听话”其实是环境没搭好。OpenAI 用 Codex 从零搭产品时也撞上同一堵墙，他们的原话是：进展比预期慢，不是因为 Codex 不行，而是环境没有被定义清楚（the environment was underspecified）[^1]。所以他们不调 prompt，而是把知识沉淀进仓库、让 agent 能独立起实例复现和验证修复、用 linter 和结构测试物理上阻止违规代码进入仓库。

[^1]: [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)

为什么代码任务特别适合 Agent？因为反馈链条清楚：改代码、跑测试、读失败、再修，每一步都有客观验证兜底。验证方式到位与否，效果差异可以很夸张。The Harness Problem 的实验里，16 个模型只换编辑工具，其中一个模型的通过率从 6.7% 升到 68.3%，模型本身一个参数都没动[^2]。产品侧 harness 的同类结论，上一篇用 LangChain 的实验也写过：固定模型只改环境，成绩照样能拉开。

[^2]: [We improved 15 LLMs at coding in one afternoon. Only the harness changed.](https://blog.can.ac/2026/02/12/the-harness-problem/)

非代码领域要获得同样的稳定性，需要同构的东西：可信的事实来源、可持续维护的文档、明确的架构约束、可重复的验证方式。由此推出一个反直觉的结论：**把任务交给 Agent 之前，先准备好事实来源和验收方式，通常比继续加提示词更有效。** 提示词是在说服，验收是在证明。

更底层的真相是，搭这套东西时你会发现，要补的文档、自动化工具、知识库没有一件是新的。这些全是传统软件工程里早就存在的问题，人工开发时一样会遇到：文档没人写、测试不覆盖、边界不清晰。以前这些账一直拖着，因为写代码本身已经够累了。现在 AI 把“写”的效率提上来，我们终于腾出精力，把一直想做但没动力做的工程改进补上。

还有一点：不必过度 FOMO。2026 年冒出的新概念不少，context engineering、loop engineering、graph engineering……大部分其实没什么营养，只是把已经做过的事情换了种说法。回顾下来，真正被大规模用上的，似乎只有 skills 和 harness。

所以 AI First 的终点，未必是让 AI 干所有的活，更可能是借着这股力量，把拖延已久的工程改进真正推动起来[^3]。测试覆盖不够，不是 AI 写不了代码，而是缺少让它验证自己工作的条件；架构太乱，不是 AI 维护不了，而是上下文塞满了仍然看不清边界。这些投入的收益，不在 AI 时代也值得拿。AI 只是给了我们一个不得不做的理由。

[^3]: [为什么你的"AI 优先"战略可能大错特错？](https://baoyu.io/blog/2026-04-13/ai-first)
